I still write code in Sublime Text. On Omarchy it opens one window per project, takes the colours of whatever theme the desktop is wearing, and has no menu bar. This is the configuration, file by file, and the small Python that holds it together.

Still Sublime, in 2026

The argument has not changed in fifteen years: it starts before the finger leaves the key, and a 1 MB generated Laravel class does not make it think. The rest of the argument is about windows. On Omarchy every work project is an entry in the launcher menu, and that entry runs subl --project <service>.sublime-project. One project, one window, one sidebar, one terminal. A script generates the project files, adding a build system per tool it finds in the folder (composer install, php artisan test, vendor/bin/phpstan), all targeting Terminus rather than the native build panel, so the output is coloured and can be cancelled.

That workflow needs one setting most people never touch:

"hot_exit": "disabled",

Hot exit resurrects your last session at startup. With it on, opening a project from the menu also reopened the last project I had closed, next to it, every time. Off, Sublime starts with exactly the window the menu asked for. The price is that unsaved scratch buffers die with the process. I have learned to save them.

Two more lines in Preferences.sublime-settings are Omarchy-specific. The font is named explicitly, JetBrainsMono Nerd Font at 12, because it is already the system font (omarchy font current) and naming it beats letting fontconfig resolve monospace on its own. And update_check is false, because the AUR package sublime-text-4 cannot be updated by the built-in updater. The setting is ignored on an unregistered copy, so the dialog shows up anyway. It showed up while I was taking the screenshots for this note.

A theme that follows the desktop

An Omarchy theme is a folder with a colors.toml: a flat list of semantic keys (bg, fg, accent, muted, red, green, orange, cyan…). When you run omarchy theme set, Omarchy renders every template it finds in ~/.config/omarchy/themed/ with those values, then runs the scripts in hooks/theme-set.d/. Alacritty, btop and Neovim get that for free. Sublime does not, so I wrote two templates and a hook.

sublime.sublime-color-scheme.tpl is the syntax side: background, caret, selection at {{ accent }}60 (Sublime reads #rrggbbaa as is), gutter, diff colours, and a dozen rules mapping scopes to palette keys. sublime.sublime-theme.tpl is the chrome: sidebar, tab bar, status bar, command palette, autocomplete, all expressed as om_* variables on top of Default.sublime-theme. The hook copies the rendered results into Packages/User under a fixed name:

cp "$THEME_DIR/sublime.sublime-color-scheme" "$SUBLIME_USER/Omarchy.sublime-color-scheme"

tint=white
[[ $(omarchy-theme-color --file "$THEME_DIR/colors.toml" mode) == light ]] && tint=black
sed "s|\"base_tint\": \"white\"|\"base_tint\": \"$tint\"|" \
  "$THEME_DIR/sublime.sublime-theme" >"$SUBLIME_USER/Omarchy.sublime-theme"

The preferences point at Omarchy.sublime-theme and Omarchy.sublime-color-scheme and never change. Sublime watches its package folder, so the editor recolours itself about a second after the terminal does. No restart, no command, nothing to click.

Sublime reloads any file under Packages/User the moment it changes on disk. That is why none of this needs a plugin on the Sublime side: the hook writes two files, and that is the end of its responsibilities.

The base_tint line is the part I would not have guessed. The Default theme derives most of its shades by tinting a base colour towards base_tint. White is right for a dark theme. On a light theme it washes everything out, so the hook asks Omarchy which mode the theme is in and flips it to black.

The tab bar was the other trap. Sublime classifies a window as dark, medium-dark, medium or light from the luminosity of the colour scheme, and picks the matching tabset_*_bg variable. Retro 82 lands on medium-dark. Set only tabset_dark_bg and the bar falls back to the Default computation, the background lightened towards white, which is how I got a grey slate on top of a navy editor for a day. The template now sets all four. The active tab gets an accent rule along its top edge (layer2.tint), the same orange as Hyprland's active border.

Before the templates there was a Python script, sublime-theme-from-omarchy, that reads a theme's colors.toml and, when the theme ships a vscode-theme.json, converts its tokenColors into Sublime rules: scope arrays joined with commas, fontStyle filtered down to what Sublime understands (bold, italic, underline, glow; no strikethrough). It also sets line_highlight to the muted colour at 18 % opacity, because editor.lineHighlightBackground in most Omarchy themes equals the editor background and the current line would be invisible. The templates replaced it for the daily case; the script stays for one-off schemes, and the Retro 82 pair it produced is still in the repo.

No menu bar

Sublime stores the menu bar's visibility in the session, per window. Since every project opens a fresh window, that memory is useless: the new window gets the default, which is visible. So a plugin of a dozen lines hides it on on_new_window_async, and again 200 ms after plugin_loaded for the window that already exists at startup, which the event never fires for.

def _hide(window):
    if window is not None and window.is_valid():
        window.set_menu_visible(False)

class HideMenuOnNewWindow(sublime_plugin.EventListener):
    def on_new_window_async(self, window):
        _hide(window)

def plugin_loaded():
    sublime.set_timeout(lambda: [_hide(w) for w in sublime.windows()], 200)

Ctrl+Alt+M is bound to toggle_menu for the rare day I need it, and pressing Alt on its own shows the bar for the length of one navigation, which Sublime does by itself.

Terminus, and a prompt for everything else

Ctrl+Alt+T toggles a Terminus panel in the project folder ("cwd": "${folder}", with hide_active so the same key closes it). The build systems handle the fixed commands. What was missing was the one-off: an artisan command I type once, a script I run and forget. That is run_in_project, a window command of forty lines.

It opens an input panel, and on Enter hands the text to Terminus:

def on_done(self, text):
    command = (self.prefix + " " + text).strip()
    self.window.run_command("terminus_open", {
        "shell_cmd": command,
        "cwd": _project_dir(self.window),
        "title": command[:40],
        "panel_name": "Terminus",
        "show_in_panel": True,
        "cancellable": True,
        "timeit": True,
    })

shell_cmd rather than cmd, so quotes and pipes go through unparsed. timeit prints the duration at the end, cancellable means Ctrl+C works. The prefix argument makes variants cheap: Ctrl+Alt+R is the bare $ prompt, Ctrl+Alt+A is the same command with php artisan prepended. The artisan variant's is_enabled checks that a file named artisan exists at the project root, so on a static site like this one the palette entry is simply greyed out.

PHP formatted on save, with the project's own formatter

Work projects do not agree on a formatter. Some run Pint, some run phpcs, and each carries its own rules in pint.json or phpcs.xml. I did not want a global formatter with a global config fighting those files, so the save hook finds the tool the project installed:

TOOLS = (
    ("pint", lambda path: [path]),
    ("phpcbf", lambda path: ["-q", path]),
)

def _find_tool(file_path):
    directory = os.path.dirname(file_path)
    while True:
        for name, args in TOOLS:
            binary = os.path.join(directory, "vendor", "bin", name)
            if os.access(binary, os.X_OK):
                return directory, [binary] + args(file_path)
        parent = os.path.dirname(directory)
        if parent == directory:
            return None, None
        directory = parent

It walks up from the saved file to the first vendor/bin that contains either, Pint first when a project has both, and runs it with the project directory as working directory so the config file applies. No vendor/ yet, nothing happens. The listener is on_post_save_async, so the save itself is never slowed. The one wrinkle: phpcbf exits with 1 when it fixed something, which is the normal case, so only return codes above 1 count as a failure. When the tool has rewritten the file, Sublime would reload it on the next focus; the plugin calls revert right away so the buffer matches the disk before I look at it. A project can opt out with "php_format_on_save": false in its settings.

Language servers and the rest

The package list is 25 entries long. The ones that matter:

PHPLSP-intelephense, with phpVersion pinned to 8.3.0: the containers run 8.3, the host CLI runs 8.5, and without the pin it suggests syntax the app cannot execute. files.maxSize raised to 5 MB for Laravel's generated classes. Undefined-symbol diagnostics on, which only works with vendor/ installed on the host.
Vue, TSVue, LSP-volar, LSP-typescript, LSP-eslint, LSP-tailwindcss.
PythonLSP-pyright and LSP-ruff. Pyright flags import sublime_plugin in the plugins above, since that module only exists inside Sublime. I live with the red dot.
DataLSP-json, LSP-yaml, DotENV, Dockerfile Syntax Highlighting, EditorConfig.
GitGitGutter in the gutter, GitSavvy for staging and blame without leaving the window.
Templates, docsLaravel Blade, MarkdownEditing.
ChromeTerminus, SideBarEnhancements, SublimeLinter, A File Icon. Vintage is in ignored_packages. ayu and SynthWave 84 are installed as fallbacks, commented out in the preferences, for the day an Omarchy theme turns out unreadable in an editor.

Every file is a symlink

Nothing in Packages/User is a real file. Each one is a symbolic link into a private git repo that holds the whole desktop: Hyprland, the menu, the hooks, the templates, the package lists. Editing a keymap in Sublime edits the repo. omarchy-setup status says what changed, omarchy-setup sync commits and pushes, omarchy-setup add adopts a new file. The generated Omarchy.* pair and Package Control's .bak files are deliberately not tracked: they are output, not source. Some tools write a file by replacing it rather than editing it, which silently breaks the link; status notices, sync re-adopts the new version. The repo deserves a note of its own; this one is about the editor.

What is missing

  • The update dialog. An unregistered copy ignores update_check, and I do not have a workaround short of a licence, which is probably the point.
  • A theme without colors.toml never reaches the templates. The hook exits early and Sublime keeps the previous theme's colours while everything else changes. Rare, and confusing when it happens.
  • The save hook runs the whole formatter on every save, which on a phpcs project is a visible second. A debounce, or a diff check before the revert, would help.
  • Blade has syntax highlighting but no language server. Intelephense does not see into templates.
  • Markdown.sublime-settings is an empty pair of braces. It has been for a month.
  • The project files and the menu entries assume my work layout. The idea travels, the script does not.
